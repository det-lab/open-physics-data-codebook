# Codebook: Data Licensing Practice in Rare-Event Physics Collaborations

*Draft v0.2, October 12, 2026 (v0.1 October 1). For discussion with Suzie Allard. Everything here is a starting point for her to change. v0.2 incorporates the fixes from a six-case pilot coding (SuperCDMS, LZ, COHERENT, LEGEND, IceCube, EXCESS repository); the pilot sheet and its issues log are in the shared folder.*

## Purpose

This codebook defines how we record, for each physics collaboration in the sample, what it has released publicly, under what terms, and who decided those terms. It is used in two passes: first by coding public documents before the SESAPS meeting (November 13, 2026), then as the basis for a questionnaire to collaborations after the meeting. The same fields appear in both passes so the two can be compared.

The research question is: when rare-event and underground-physics collaborations release data, what license and reuse terms do they attach, and what drove that decision?

## Unit of analysis

Two tables. The collaboration table has one row per collaboration (for example, COHERENT, LEGEND, IceCube) and holds sections A and B, C1 and C2, and a coding record (E). The release table has one row per public data release, keyed to the collaboration, and holds sections C and D with its own coding record (E), because terms and reuse attach to a specific release and one collaboration can have several with different terms. Section F is questionnaire-only and belongs to the collaboration. The questionnaire should go to individuals (spokesperson, data manager) and be aggregated, since a collaboration cannot answer a survey. Code the collaboration as it is now: sections A and B describe the current or most recent experiment and its current policy, because earlier experiments did not fall under the new DOE and NSF public-access rules. Earlier releases are still coded in the release table, with their dates, so that practice before and after the rules can be compared.

## Sources, in order of authority

For pass 1, check these sources for each collaboration and record which were found. Search them in this order. Each field's rule names which source its value comes from; when two sources disagree, record the value from the source the rule names and log the disagreement in E6. A disagreement between a collaboration's own documents is a finding, not an error, and becomes a question for that collaboration in the questionnaire.

1. A collaboration data policy, data access policy, or publication policy, if public.
2. The repository record of each public release (Zenodo, Harvard Dataverse, HEPData, OSTI Data Explorer, HEASARC, a lab DOI service, GitHub, or a collaboration-run portal or web directory). The license field, the README, and any terms of use.
3. A data-release paper or companion document that describes the release.
4. The data-availability statement in the collaboration's main physics papers.
5. The collaboration's public website.

## Fields

Each field has a name, allowed values, and a rule for choosing among them. "Unknown" means the coder looked and found nothing; it is distinct from a blank, which means the coder has not looked yet. "To check" is written by the AI pass in any cell it could not resolve because a page or file was unreachable, with a matching line in the to-check list (URL, field, what to look for); the human coder opens the link and replaces it with a value, with "Unknown" if the page gives nothing, or with "Could not open" if a file was obtained but unreadable. A finished row has no "To check" cells.

### C. Releases

Section C is coded once per release, in the release table. C1 and C2 are the exception: they sit on the collaboration row as the count of releases and the year of the most recent. Find releases by searching, in order: (1) the collaboration website's data page; (2) Zenodo, Harvard Dataverse, HEPData, OSTI Data Explorer, and HEASARC for the collaboration name; (3) one web search for "\<collaboration\> data release." Stop after those three or 20 minutes. A release is a repository record with its own DOI or persistent landing page, or an entry on the collaboration's own data page with a persistent URL, whatever it is titled: a HEPData record or a Zenodo record called "Supplemental Material" is a release; a journal-hosted supplement with no repository record is not; arXiv ancillary files count only when the collaboration's data page or policy names that channel. Versions of one record count once (code the latest). Software-only records are not releases. A release belongs to the row whose name is on the record and the paper byline (a Majorana record is Majorana's, not LEGEND's). Record "DOI minted: Yes/No" for each. A release counts for a collaboration when it is listed on the collaboration's data page, or the record's creator is the collaboration, or a collaboration paper or companion document describes it; a record by one member institution that meets none of these (a dataset deposited under an individual's ML grant) is an "affiliated release", listed in E5 and not coded. Code every release found, up to ten; if there are more, take the most recent release of each repository type in C4 plus the most recent five overall, record the total in C1, and list the rest by DOI in the notes; "most recent" means the repository record's publication date, or the data-page date if there is no record. D1 and D2 are coded per release in the same table. C10 records the scientific content of each release, so that a calibration release is not read as a collaboration policy.

### F. Questionnaire-only items

Not coded in pass 1. A public document will rarely answer these, so searching costs coding time and finds little. The rule: a field stays in pass 1 if a public document could plausibly answer it, and moves here if not. The questionnaire asks each collaboration:

F1 Institutional approval for the release: lead institution only, lead and member institutions, or none.

F2 Which office was involved: research office, technology transfer, legal counsel, lab management, none.

F3 Who chose the license and attribution terms, and why.

F4 Which agency's data-management plan the collaboration treats as governing.

F5 Why the data level in C3 was chosen, and what a user would need that the release does not include.

## Workflow

1. A first pass over every collaboration on the list, done as a hybrid: an AI pass fills every field it can reach, with a source URL for each non-blank value, and produces a to-check list of the pages it could not open (repository records, downloads, citation lists), one line per field with the URL and what to look for. A human coder then opens those links, fills the cells (typically C5a, C6, C9, D1, D2), runs the read test (C9f), and marks each as human-checked in E1. The AI pass must never guess a value for a page it could not open; "To check" is the correct entry. Budget for the human step: about 10 minutes per release.
2. A second coder, working independently from the codebook alone, codes a random 20 percent of the collaborations, including all of their releases. The team compares the two and records agreement per field.
3. Where the two coders disagree, the rule in this codebook is revised until both would have reached the same value, and the affected rows are recoded.
4. The agreed first-pass results become the opening slide at SESAPS and the first entries in the license catalog.
5. After the meeting, the questionnaire asks each collaboration to confirm or correct its row and to answer the questionnaire-only items in section F.
